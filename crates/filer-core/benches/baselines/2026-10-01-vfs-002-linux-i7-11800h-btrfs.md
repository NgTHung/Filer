# Batched Local Enumeration, 2026-10-01

A 256-row metadata first page of a 10,000-entry directory took 1.97 ms, while the fast first page took 0.36 ms. Both read the same entries, but the metadata page sent every `DirEntry::metadata` call through `tokio::fs`, which makes one blocking-pool hop per row. This record measures VFS-002, which reads each page and its metadata inside one blocking task, on one Linux machine.

## Machine Profile

- OS: Linux 6.12.107+deb13-amd64, x86_64
- CPU: Intel Core i7-11800H, 16 logical CPUs
- Rust: rustc 1.98.1 (LLVM 22.1.8)
- Cargo: 1.98.1
- Filesystem: Btrfs on NVMe, compression zstd level 1
- Before revision: `355e913`, per-entry `tokio::fs` enumeration
- After revision: `9989c25`, `std::fs::ReadDir` in one blocking task per page or batch

The runs generated 10,000 empty `.dat` files in an isolated Git worktree and used a 256-entry page, 3 warmups, and 20 timed samples.

```bash
FILER_BENCH_FIXTURE_ROOT=target/bench-fixtures cargo bench -q -p filer-core --bench large_directory
```

## Results

Each revision ran at least twice. The table shows one run of each, and the other runs matched its metadata first-page median within 0.08 ms.

| Scenario | Revision | Median ms | p95 ms | Allocations | Allocated bytes |
| --- | --- | ---: | ---: | ---: | ---: |
| Metadata first page | before | 1.973 | 1.993 | 2,974 | 631,588 |
| Metadata first page | after | 0.466 | 0.611 | 2,132 | 488,606 |
| Fast first page | before | 0.359 | 0.363 | 2,452 | 506,804 |
| Fast first page | after | 0.270 | 0.313 | 2,124 | 487,696 |
| Fast next page | before | 0.251 | 0.272 | 2,374 | 326,356 |
| Fast next page | after | 0.209 | 0.217 | 2,111 | 310,210 |
| Sorted first page | before | 12.082 | 12.711 | 90,484 | 21,458,026 |
| Sorted first page | after | 8.309 | 8.437 | 80,210 | 20,826,766 |
| Full snapshot | before | 9.442 | 9.715 | 90,380 | 10,331,084 |
| Full snapshot | after | 7.385 | 8.564 | 80,066 | 9,690,164 |

The metadata first page is 4.2 times faster. It now costs 0.20 ms more than the fast page, which is the price of 257 `statx` calls, where it used to cost 1.61 ms more. Fast listings gain less, because `tokio::fs::ReadDir` already read 32 entries per hop and cached each entry's type. They still drop about one allocation per row, which was the shared `DirEntry` handle `tokio::fs` wraps around each entry.

A first attempt reserved at most 256 rows per batch. The first page requests 257 rows, its page plus one lookahead row, so the buffer doubled and the page allocated about 68 KB more than before. Batches now reserve their full requested size, up to 4,096 rows.

The Windows NTFS comparison, which decides whether a native `FindFirstFileExW` path beats `std::fs::ReadDir` in one blocking task, is not part of this record.
