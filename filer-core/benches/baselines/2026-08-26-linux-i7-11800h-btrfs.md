# Large Directory Baseline, 2026-08-26

This baseline measures commit `44b7f26` through the public `Command::Scan` and
`Event::DirectoryLoaded` or `Event::DirectoryPageLoaded` contracts.

## Machine Profile

- OS: Linux 6.12.101+deb13-amd64, x86_64
- CPU: Intel Core i7-11800H, 16 logical CPUs
- Rust: rustc 1.97.1, LLVM 22.1.6
- Cargo: 1.97.1
- Filesystem: Btrfs on NVMe, compression zstd level 1
- Fixture: 10,000 empty files, page size 256
- Sampling: 3 warmups, 20 timed samples per scenario

The command used a fixture root on Btrfs instead of the system tmpfs:

```bash
FILER_BENCH_FIXTURE_ROOT=target/bench-fixtures cargo bench -p filer-core --bench large_directory
```

Fixture generation took 79.826 ms and was excluded from every timed sample.

## Gate Status

The first-page gate fails. The structural public-command test observed 10,000
of 10,000 provider rows before Filer emitted a 256-row page. Fast first-page p95
was 13.4 times the full-snapshot p95 on this profile. Next-page p95 was 13.8
times the full-snapshot p95 because continuation repeats the directory walk.

Metadata first-page p95 was 66 percent slower than fast first-page p95 because
the full walk also performs per-entry metadata work. Sorted first-page latency
was close to the empty-pipeline path, which shows the empty path already pays
most of the global selection cost.

The current paging design bounds retained rows, but it does not bound work by
page size. `PIPELINE-002` owns provider-cursor and paging-session work needed to
change that. The decoration on/off gate remains unmeasured because
`MODULES-002` has not landed.

Treat these values as a comparison baseline for the same machine profile. The
structural test is the portable gate. Absolute latency should not gate other
machines or filesystems.
